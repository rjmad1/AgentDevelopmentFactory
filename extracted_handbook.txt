1. Executive summary
Your goal: use Hermes as the home base for designing, building, evaluating and operating agents that can be
adapted to different vendor runtimes.
The recommendation is a small, vendor-neutral factory with one written agent contract, explicit runtime
adapters, shared acceptance tests and a supervised release gate. Start with one agent and one adapter. Add
another runtime only when the same acceptance pack can show what transfers and what does not.
"Any vendor runtime" is a design requirement, not a compatibility claim. Model API compatibility does not mean
agent-runtime compatibility. Tool calling, permissions, memory, interrupts, sessions, deployment and billing
differ. An adapter must declare unsupported features and stop rather than silently weaken a requirement.
This guide covers the full lifecycle: use-case discovery, requirements, design, tools and data, implementation,
evals, security, delivery, operations, improvement and retirement. Infrastructure supports that lifecycle; it is not
the goal by itself.
STATUS: PREPARATION ONLY. Nothing here installs software, changes a machine, creates an account, starts a
test or authorizes spending. No runtime adapter in this guide has been built or tested on your machine. AegisOS
is out of scope and remains untouched.
FREE-FIRST RULE: use existing resources and OSS where suitable. Free software can still incur model, storage,
electricity, hosting and review costs. Only currently verified free-provider entitlements may be considered; do
not activate payment-backed trials or automatic paid fallback. No client or private data goes to unchecked
providers.
Use this guide in order: read the state and architecture chapters; choose the first agent; review its contract and
permission boundary; approve a bounded next step. The copy-ready prompts at the end stop at planning
unless you separately authorize work.
Prepared for Raja Jeevan Kumar Maduri | 3 November 2026, IST. Official sources were checked on 3 November.
Installed-state evidence is dated separately. This is a proposed operating design, not a certification or
live-system inventory.
A framework supplies building blocks. A factory repeatedly turns an approved objective into a versioned, tested,
operated agent with a named owner. Business outcomes are less repeated setup, lower human rework and
honest comparison; success is useful accepted output, not agent count. This is a blueprint, not a live factory.

3. Foundational design principles
Principles with checks: neutral contracts plus tested adapters for independence; reuse reviewed capabilities
before adding dependencies; approved specs before builds; least privilege and synthetic data first; final-state
evidence before acceptance; pinned dependencies and fixtures; finite retries and scoped changes;
failure-to-regression learning; efficiency per accepted result; resume from verified state before replay. Unknown
policy fields fail validation rather than being ignored.
Current: design recorded. Target: enforce these at adapter/tool/release boundaries. Gap: implementation and
prospective validation.

4. Capability taxonomy
MODEL is inference; PROVIDER is the account/endpoint; FRAMEWORK is a programming library; HARNESS
supplies execution/context/tools; RUNTIME is the concrete implementation/version; HOST runs it. SKILL is a
reusable procedure; TOOL is a callable capability; MCP SERVER exposes protocol tools/resources;
WORKFLOW defines stages; MEMORY stores scoped facts/state; KNOWLEDGE stores sources/indexes; EVAL
SYSTEM supplies fixtures/runners/graders; REGISTRY supplies versioned discovery; FACTORY governs
creation through retirement.
Classification: kind, effect level, data class, maturity and evidence. Effects: public-read, private-read, local-draft,
resource-change, send/publish, financial/destructive. Unknown permissions are ineligible for automatic
routing.
Maturity: M0 described; M1 bounded prototype; M2 repeatable pinned/evidenced flow; M3 supervised operated
flow; M4 production-ready for stated scope with measured SLO/recovery; M5 enterprise-grade for stated scope
with demonstrated tenancy/governance/compliance/assurance. No current-machine score or certification
assigned. This factory is design-stage, with mock references only.

5. Factory reference architecture
Think of the factory as a production line with quality gates, not a permanently running crowd of agents.
1. REQUEST AND CONTRACT: capture the problem, user, inputs, outputs, success criteria, permitted actions,
data category and cost ceiling. The approved contract is the source of truth.
2. DESIGN AND BUILD: choose the smallest workflow, tools and state model. Generate a runtime-specific
package from a vendor-neutral definition. Keep generated files separate from authored policy and tests.
3. CHECK AND RELEASE: deterministic tests, behavioral evals, security review and a human decision produce a
versioned release. An agent cannot approve its own expanded authority.
4. OPERATE AND LEARN: queue work, retain evidence, monitor outcomes/costs, pause on drift, and convert
real failures into regression cases. Retire agents and revoke their access when no longer useful.
Proposed logical path:
Raja's approved request
  -> agent contract + policy + eval pack
  -> adapter/compiler for selected runtime
  -> isolated candidate build
  -> deterministic + behavioral + security checks
  -> human release decision
  -> supervised operation + evidence archive
  -> feedback -> reviewed new version
Hermes can coordinate this path. Its profiles can hold specialist state; its current documented Kanban can
manage durable work; its delegates can assist with bounded tasks. These are Hermes features, not permission
to enable them here. [S1-S5]
Keep three planes separate: CONTROL decides scope/status/approvals; EXECUTION runs the adapter in its
boundary; EVIDENCE stores outputs, hashes, results and release decisions. A board's Done field must not
substitute for the evidence plane.
The gateway routes model calls. It does not automatically translate a Hermes agent into another framework,
enforce tool permissions in that framework, or validate output truth. An external harness adapter is separate
from a provider adapter.
Begin with one local repository, one evidence folder and one reviewed task queue. Do not introduce
Kubernetes, a vector database, a hosted trace stack or an always-on server merely because they appear in
reference architectures.
Component owners: intake(scope/request ID), validator(schema/semantics), resolver(eligible registry entries),
planner(dependencies), builder(candidate), adapter(target mapping), evaluator(separate
efficacy/safety/efficiency), release controller(authorized acceptance), operations and evidence archive.
Boundaries: owner->control, external data->parser, control->runtime, runtime->tool/service,
candidate->release, local->remote data.
Ecosystem: Hermes coordinates. OmniRoute and user-mentioned LiteLLM overlap as model gateways; select
one primary route and document deliberate chaining to avoid duplicate retries/budgets/telemetry. LiteLLM
installed state is unverified; current virtual-key/budget docs: https://docs.litellm.ai/docs/proxy/virtual_keys .
FreeLLMAPI is a provider-capacity route only after verification. OpenClaw/Antigravity are user-named harness
targets whose version/interface/policy support remains unverified. MCP connects tools, registry discovers
eligible versions, neither grants authority. One task lifecycle authority; Notion/Trello may be projections, not

6. Hermes harness architecture
Current Hermes docs distinguish profiles, workspaces and sandboxes. A profile isolates Hermes state; a
workspace selects where work happens; a sandbox limits access. Profiles are not an OS security boundary.
[S1-S3]
Separate long-lived roles into separate profiles only when they need distinct state or credentials. Current docs
warn against two agent processes sharing one Hermes home because automatic memory writes can
compound state. Review clone behavior carefully: some clone operations copy keys, skills and memory. A clean
candidate should not inherit live secrets by convenience.
For code: one Git worktree and branch per change. Review the diff, protected-file hashes and test output before
merging. A worktree prevents many file collisions; it does not restrict network access, credentials or host
filesystem permissions. [S9]
Delegated Hermes children have fresh conversational contexts, but the current configuration guide says they
can share the parent's container. Persistent Docker modes can also share state across sessions. "Isolated
context" therefore does not mean isolated filesystem or separate secret boundary. Verify the exact
backend/mode used. [S2, S3]
Proposed project layout, not a command to create it:
agent-factory/
  contracts/       # approved neutral definitions
  adapters/        # target-specific translation/execution
  policies/        # reviewed capability boundaries
  tools/           # validated tool interfaces
  evals/           # frozen fixtures and graders
  tests/           # adapter and application tests
  templates/       # generated-package templates
  docs/            # architecture and operating guides
  releases/        # manifests and release decisions
  evidence/        # run logs and artifacts, secrets excluded
Keep ephemeral scratch separate from durable evidence. Current Hermes Kanban docs describe scratch
cleanup on completion and durable attachment handling for declared artifacts. Inspect your installed behavior
before relying on those semantics. Do not leave the only evidence copy in a temporary directory. [S4]
Initial concurrency policy: one writer per worktree, bounded read-only parallelism only when needed, explicit
cancellation and no duplicate execution after restart. Persistent queues need idempotency and claim
ownership, not merely unique-looking task titles.
A tool is an authority boundary. For each capability document: input schema, output schema, caller identity,
permitted resources, side effects, rate/cost limits, idempotency behavior, timeout, cancellation, redaction and
audit event.
Classify capabilities: READ PUBLIC; READ PRIVATE; WRITE LOCAL DRAFT; CHANGE ACCOUNT;
SEND/PUBLISH; SPEND/DELETE. A research agent usually needs only the first and local draft output. More tools
increase both failure surface and context overhead.
For MCP inventory, record server owner, exact package/version, transport, source/license, enabled tools,
filesystem/network reach, credential scope, last bounded probe and data destination. "24 configured servers" is
not a health or security verdict.
Current MCP security guidance forbids token passthrough, requires appropriate audience validation and
addresses confused-deputy consent, SSRF and authorization of state handles. Apply remote OAuth controls

7. Universal agent specification
An agent definition should describe behavior and constraints without depending on a vendor's prompt format.
Store it as structured data plus readable Markdown. The following is a proposed factory schema, not native
Hermes configuration and not executable as-is.
schema_version: 1
agent_id: research_brief_v1
owner: Raja
purpose: Produce a sourced brief from approved public URLs
inputs:
  topic: string
  approved_urls: list
outputs:
  brief: markdown
  source_ledger: json
policy:
  mode: draft_only
  data: public_or_synthetic
  tools: [read_approved_url, write_artifact]
  effects: []
  secrets: none
  on_denial: stop_and_report
limits:
  max_steps: 20
  max_parallel_workers: 1
  paid_spend: 0
state:
  durable_fields: [request_id, stage, evidence_refs]
acceptance:
  suite: evals/research_brief_v1
  required: [grounding, coverage, no_external_effects]
targets:
  hermes: candidate
  other_runtime: unsupported_until_tested
The limits are illustrative proposed starting settings, not approved allocations or a production config. Define a
wall-time/token ceiling appropriate to each task before enabling execution. Zero paid spend still consumes free
quota and local resources.
Additional files: contract.md for the human specification; policy.yaml for boundaries; tool schemas;
data-classification rules; golden fixtures; grader rules; adapter capability manifest; dependency lock; release
notes and rollback.md.
The spec must say what happens on missing evidence, timeout, rate limit, ambiguity, denied tool access,
interrupted session and unavailable provider. UNKNOWN and BLOCKED are valid outcomes. A factory that
always produces an agent is unsafe; sometimes the correct output is an incompatibility report.
Version changes to behavior and permissions separately. A minor wording edit can alter behavior enough to
require regression testing. A broader audience, new tool, data category or financial effect always needs a new
scope decision.
The complete proposed schema is schemas/agent.schema.json, not native Hermes config. Required areas:
identity, purpose, behavior, architecture, models, tools, memory, knowledge, execution, evaluation, security,
deployment and operations. Semantic validation must check approval references, registry versions, data
destinations, compatibility and cost, beyond JSON shape. Unknown major version or unsupported required
capability blocks. Schema major upgrades require migration; agent/adapter versions and model-route changes
trigger relevant regressions.

8. Vendor-agnostic interoperability
Separate four things: MODEL PROVIDER supplies inference; AGENT RUNTIME owns the execution loop; TOOL
PROTOCOL connects capabilities; DEPLOYMENT HOST runs the process. Swapping an OpenAI-compatible
URL addresses only part of the first layer.
Proposed portability levels:
- P0 Definition: the target can read a translated task/prompt and return text.
- P1 Tools: required tool schemas, validation, errors and structured outputs work.
- P2 Policy: approval, denial, data limits and stop rules are enforced in the target.
- P3 Continuity: durable state, interruption/resume, duplicate handling and evidence survive the required
lifecycle.
- P4 Operations: packaging, deployment, monitoring, rollback and retirement meet the contract.
A target is compatible only at the tested level. Unsupported behavior blocks release or leads to an explicitly
narrower agent contract approved by you.
Adapter responsibilities: validate the neutral spec; detect runtime/version; map instructions, tools and outputs;
bind secret references at runtime; enforce or report limits; create isolated session/workspace IDs; normalize
events; collect artifacts; classify failures; cancel cleanly; export evidence. Do not export internal model
reasoning as a portability requirement. Tool/action/outcome evidence is enough for most gates.
Normalized event proposal: request_id, run_id, agent_version, target/version, timestamp, stage, event_type,
redacted tool arguments, result/error class, evidence reference and cost/usage when actually available. Use
unknown rather than zero for missing usage.
No silent fallback across runtimes. A replacement can change permissions, data retention, tool semantics and
cost. Revalidate the policy and acceptance pack first.
Do not migrate live vendor sessions by copying transcripts, auth files or private memory. Recreate an approved
minimal task state in the destination and test semantic equivalence. Native session formats are not
interchangeable.
Conformance must test the real adapter boundary. A mocked model is useful for plumbing; it does not prove
real tool calling, cancellation, recovery or provider eligibility.
These are documentation-grounded candidate families, not installed integrations or a promise of free inference.
Exact authentication, model entitlement and SDK versions must be checked for each target. [S17-S19, S21]
HERMES NATIVE: map the spec to an approved profile/workspace and permitted tools. Decide whether work is
a short delegation or a durable Kanban task. Verify actual installed version, profile state, artifact persistence and
terminal permissions. Current docs are not proof that October's install exposes every current feature.
OPENAI AGENTS SDK: manager-style agents-as-tools keep the manager responsible; handoffs transfer control
for a branch. Choose deliberately. Map your neutral tool schemas, approval rules, session state and result
contract. Provider/account charges remain a separate gate. [S17]
CLAUDE AGENT SDK / CLAUDE CODE: map permission modes, hooks and allow/deny rules. Do not assume an
approval callback sees every action: current docs explain that earlier auto-approval can skip it. Do not default to
bypassPermissions or broad allowlists. Model subscription access is not blanket API entitlement. [S18]

11. Autonomous agent creation workflow
Use roles as responsibilities first. One supervised session can perform several roles with separate stages; do not
create six permanent agents before proving the workflow.
PRODUCT OWNER: chooses the problem and approves success, cost and effect boundaries. ARCHITECT:
writes the contract and adapter plan. BUILDER: changes only approved files. EVALUATOR: runs frozen tests and
checks actual outcomes. SECURITY REVIEWER: examines data/permissions/dependencies. RELEASE OWNER:
accepts evidence and controls deployment. Operator and retirement owner must also be named.
Proposed lifecycle: IDEA -> SPEC DRAFT -> SPEC REVIEW -> APPROVED BUILD -> CANDIDATE ->
EVALUATING -> REVIEW -> APPROVED RELEASE -> SUPERVISED ACTIVE -> PAUSED / RETIRED. Any stage can
become BLOCKED. These are proposed factory states, not a replacement schema silently applied to your
board.
GATE A, BEFORE BUILD: contract approved; runtime selected; version/source pinned; workspace and
permitted files explicit; synthetic fixtures ready; data and spending limits explicit. No implied permission from a
draft card.
GATE B, BEFORE RELEASE: functional tests and behavioral gates pass; security findings triaged; evidence
complete; unsupported capabilities disclosed; backup/rollback route tested in scope; release decision
recorded by an authorized person.
GATE C, BEFORE AUTONOMY: repeated prospective runs show the required behavior, not just repaired code.
Start with a low-risk canary and a clear stop condition. Existing SDD process gaps need their separate
supervised validation; this guide does not claim that validation happened.
GATE D, BEFORE CHANGE: diff, impact, relevant regressions, migration/rollback and cost changes reviewed. A
model route swap is a behavior change even if no code changed.
The builder cannot edit the grader to make its candidate pass. Preserve protected fixtures and original failure
logs. The evaluator may identify an ambiguous test; changing it requires a documented review, then a new test
version and an honest comparison.
Example first product: a public-source research brief that writes only local draft artifacts. No accounts,
publishing, messages, private-data retrieval or machine maintenance. This is a proposal for your choice, not a
task queued for execution.
Stage entry/exit/owner/artifact/failure matrix is templates/stages.csv. Resume by reading state files and
checking completed-task evidence; missing proof becomes REVIEW_REQUIRED, not a replay of all work.
Approval records remain separate from model summaries.

12. Agent architecture patterns
Pattern selection guide, examples are proposed:
Reactive: synthetic FAQ classification; low overhead, weak for hidden state.
Tool-using: approved-URL brief; grounded results, tool/injection risk.
Planning: conversion plan then approved steps; handles compound work, plan drift risk.
RAG: cited public-policy comparison; freshness, retrieval/scope errors.
Stateful: draft-review loop; continuity, stale approval/state corruption risk.
Multi-agent: researcher and verifier; specialization, coordination/shared bias cost.
Hierarchical: coordinator decomposes a report; missing worker context can compound errors.
Supervisor-worker: evidence-checking owner; clear responsibility, supervisor bottleneck.
Parallel: independent public-source reads; lower wall time, quota/collision/cost risks.
Event-driven: approved new-file ingestion; efficient, duplicate/out-of-order events.
Long-horizon: multi-stage report with durable checkpoints; recovery drift risk.
Human-in-loop: draft before external send; authority retained, human wait measurable.
Multimodal: synthetic screenshot QA; visual capability, OCR/vision errors/context cost.
Autonomous coding: spec/test/scoped build/regression/review; useful repeatability, test cheating/guard
bypass/history-loss risk.
Choose the smallest fit; composition retains the strictest policy. Templates and acceptance cases must name
the relevant failure modes, not merely the pattern label.

13. Agent testing and evaluation framework
Use several grades, not one reassuring score: functional correctness; required workflow/authority; security/data
behavior; quality/grounding; reliability/recovery; cost/latency. Passing code tests does not pass approval or
recovery tests. [S14]
Deterministic graders: schema validity, exact bytes/hashes, exit code, protected-file diffs, final-state checks,
duplicate effect count and required evidence presence. Model graders: narrow quality questions with evidence
and Unknown. Calibrate them with human review; a second model family is not automatically independent truth.
Do not lock tests to one arbitrary tool sequence. Enforce sequencing where the contract requires it, such as
approval-before-write, preservation-before-repair and evidence-before-Done. Grade valid alternative
implementations fairly.
PROMPTFOO VERDICT: CONSIDER a pinned local Community trial after review; do not install automatically.
Official docs describe local evaluation, custom Python providers and no-charge Community features. Model
